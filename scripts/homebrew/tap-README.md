# Cube Homebrew tap

[Cube](https://github.com/cubeyard/cube): self-hosted coding-agent threads,
each in its own virtual machine on your Mac. Apple Silicon only.

```sh
brew trust cubeyard/tap      # Homebrew asks you to trust a third-party tap once
brew install cubeyard/tap/cube
cubed runners init-local
brew services restart cubeyard/tap/cube-berth cubeyard/tap/cube
```

This installs `cubed` (the control plane, with its own Node runtime and
`cube-gateway`), `cube-berth` (the runner, `berth vm`, with keel's guest
kernel and base), QEMU, erofs-utils and `gh`. `cubed runners init-local` sets
up the runner under `~/.cube` and enrolls it. Thread machines run cube's
default image, official Debian trixie pinned by berth, which berth prepares
for cube itself (sudo, git, gh, curl and ca-certificates from pinned Debian
packages) the first time it starts; `--image` naming your own image is for
those who build one. The same commands work for an upgrade and after `brew uninstall`:
`init-local` changes nothing that is there and says so, and `brew services
restart` starts the services or replaces ones left running. Then follow
[macOS with Homebrew](https://github.com/cubeyard/cube/blob/main/docs/macos.md)
to connect a model in the browser.

## If you have `cube-runner` from this tap

`cube-runner` is the protocol-3 runner that earlier releases installed. It is
no longer updated, and `cube` no longer depends on it. Archive its threads and
retire it in cubed
([runner operations](https://github.com/cubeyard/cube/blob/main/docs/runner-operations.md)),
then `brew services stop cubeyard/tap/cube-runner` and
`brew uninstall cubeyard/tap/cube-runner`. Its state in `~/.cube/runner`,
`~/.cube/runner.json` and `~/.cube/control.key` stays; delete it yourself
when you no longer need it. `cube-berth` never reads or touches it.

## If you installed the old `cube` launcher from this tap

Until the first release with `cubed runners init-local`, this tap's `cube`
formula was a different product: a launcher (`cube up`) with its VM under
`~/.cube`. `brew upgrade` replaces it with cubed and `bin/cube` goes away.
Before upgrading: `cube down`, then move `~/.cube` aside to keep the old VM's
data (`cube destroy --yes` deletes it), then `brew uninstall cube`. If you
already upgraded: the old VM may still run and hold port 7777 (or the
`CUBE_PORT` in `~/.cube/config`); if `ps -p "$(cat ~/.cube/vm.pid)" -o command=`
shows a qemu process, `kill` that pid (a forced stop), then move `~/.cube`
aside.

## Updates and removal

```sh
brew update
brew upgrade cubeyard/tap/cube cubeyard/tap/cube-berth
brew services restart cubeyard/tap/cube-berth cubeyard/tap/cube
brew services stop cubeyard/tap/cube cubeyard/tap/cube-berth
brew uninstall cubeyard/tap/cube cubeyard/tap/cube-berth  # keeps ~/.cube-host and ~/.cube
```

`brew update` fetches this tap now; without it Homebrew may not see a new
release for up to a day and says the old version is already installed.
`brew uninstall` does not stop running services; stop them first, or run
`brew services restart` after installing again.

## Maintaining the formulas

`Formula/cube.rb` and `Formula/cube-berth.rb` are generated by
`scripts/homebrew/formula.ts` in the Cube repository from a published stable
release's signed manifests, and pushed here by that repository's `homebrew`
workflow when a release is published. They pin the release's exact asset URLs
and SHA-256s; never use a moving `latest` URL. Do not edit them by hand.
`Formula/cube-runner.rb` is no longer generated and stays at its last release.
